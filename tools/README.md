# Инструменты на компьютере

Все команды ниже выполняются из каталога `sorter`. Нужен Python 3.10 или новее. Инструменты калибровки, анализа и тестирования не подключаются к платам. Наличие синтетического примера не означает, что камера или робот проверены физически.

## Установка и автономная проверка

```powershell
python -m pip install -r tools/requirements.txt
python -m unittest discover -s tests -p test_tools.py -v
```

Управление питанием, запись прошивки и выбор COM-порта автоматически не выполняются. В данном рабочем окружении NumPy и Pillow уже установлены; pyserial пока не установлен. Для повторения на своём компьютере достаточно приведённой команды установки.

Чтобы получить пустую папку для реальных измерений, выполните:

```powershell
python -m tools.new_session measurements/session_01 --planned-trials 100
```

Программа создаёт пустые `calibration_points.csv`, `run_log.csv` и анкету `session.json` с неизвестными полями `null`. Существующую папку она отвергает без перезаписи. Число 100 — выбранное количество планируемых испытаний, а не число выполненных переносов.

## Калибровка по точкам

Для разметки снимка откройте `tools/calibration_picker.html` двойным щелчком в браузере. Страница работает локально, не отправляет изображение в сеть и не требует установки библиотек. Загрузите исходный PNG/JPEG, нажмите на центр метки, вручную введите измеренные X/Y и выберите `train` либо `test`. Есть удаление, отмена последнего изменения и экспорт CSV. Пиксельные координаты учитывают масштаб картинки на экране. Экспорт доступен с 6 train + 3 test; рекомендуется 9 + 4. Повторные центры и одинаковые X/Y запрещены. Разрешение, отличное от 320×240, отмечается предупреждением. Страница сохраняет соответствия, но не вычисляет и не подтверждает калибровку. Данные держатся во вкладке: сохраняйте CSV до её закрытия. Отдельный режим RGB показывает цвет выбранного пикселя без добавления метки.

Подробная методика — в `docs/calibration.md`. Сначала можно проверить работу инструмента на искусственных данных:

```powershell
python -m tools.calibrate examples/synthetic_calibration_points.csv --output output/demo_calibration.json --header output/DemoCalibration.h --provenance synthetic --plane-height-mm 10
```

Выход: матрица преобразования пикселей в миллиметры, область допустимого применения, отдельные ошибки обучающих и контрольных точек, идентификатор калибровки и заголовок C++. По умолчанию используются 320×240. Программа требует минимум шесть точек `train` и три другие точки `test`. Рекомендуется девять обучающих и четыре контрольных точки. Контрольные точки не используются при расчёте матрицы.

Для реальных измерений скопируйте пустой `examples/calibration_points_template.csv` в свой каталог, заполните его и укажите `--provenance measured`. Укажите фактически измеренную высоту плоскости видимых верхних поверхностей деталей через `--plane-height-mm`.

```powershell
python -m tools.calibrate measurements/calibration_points.csv --output output/measured_calibration.json --header output/GeneratedCalibration.h --provenance measured --plane-height-mm 10 --max-test-error-mm 2
```

Значение 10 мм выше — только пример команды. Оно должно соответствовать вашим деталям. Порог 2 мм — предварительный критерий; допуск зависит от губок захвата и повторяемости руки. Нельзя считать его гарантией захвата.

`--valid-rect U0 V0 U1 V1` задаёт меньшую прямоугольную область внутри выпуклой оболочки обучающих точек. Все контрольные точки должны лежать внутри этой области. Без параметра областью служит сама выпуклая оболочка; максимум 16 вершин. За пределами области преобразование нельзя использовать для движения.

Коды завершения: `0` — численная проверка пройдена, `2` — некорректные данные/ошибка файла, `3` — матрица рассчитана, но ошибка независимых точек превышает порог. При коде `3` JSON и запрошенный заголовок сохраняются для диагностики; использовать их как принятую калибровку нельзя. Во всех случаях `CALIBRATION_CONFIRMED=false` остаётся в заголовке. Только после реальной проверки координат и ограничений стенда пользователь может изменить этот флаг в локальной конфигурации камеры. Для синтетических данных этого делать нельзя.

## Получение кадра камеры

Дополнительно установить поддержку последовательного порта:

```powershell
python -m pip install "pyserial>=3.5,<4"
python -m tools.serial_tool capture --port COM7 --output measurements/frame.png
```

`COM7` — заменяемый пример, не обнаруженный на компьютере порт. Команда передаёт только `CAPTURE` по USB-порту камеры на скорости 460800 и принимает RGB565BE. Порт нужно явно выбрать по фактически подключённой плате. Захват не передаёт `ARM` или другие команды движения. Открытие USB-порта некоторыми адаптерами может перезагрузить ESP32, поэтому питание приводов при такой проверке должно быть отключено.

Сохраняются PNG, исходный `.rgb565` и JSON с шириной/высотой. Разрешение определяется из заголовка камеры; оно должно совпадать с разрешением калибровки. Диагностический кадр 160×120 нельзя напрямую использовать для калибровки рабочей прошивки 320×240. Для окончательной калибровки захватывайте кадр из рабочего `camera_node` в его разрешении.

Для `CAPTURE` и `SCAN` в `camera_node` межплатный UART должен быть выключен: `CAMERA_UART_PINS_CONFIRMED=false`. Это отдельная сборка для настройки камеры. Иначе прошивка вернёт `USB_CAMERA_COMMAND_REQUIRES_UART_DISABLED`, и инструмент покажет эту ошибку. После открытия порта инструмент ждёт 2 секунды перед командой; при необходимости время можно изменить через `--settle-seconds` в пределах 0–30.

## Пассивное наблюдение UART v1

```powershell
python -m tools.serial_tool monitor --port COM8 --baud 115200 --seconds 30 --output measurements/uart.jsonl
```

Монитор ничего не записывает в UART. Он разбирает кадры Q/D/E и выводит число повреждённых пакетов. Для наблюдения линии между платами нужен подходящий адаптер UART с уровнями 3,3 В: его RX подключается к наблюдаемой линии TX, GND к общей земле. TX адаптера не подключать. Не подавать сигнал RS-232 или 5 В на входы ESP32. Один RX видит только одно направление; нужен второй канал/адаптер, чтобы одновременно наблюдать обратные ответы. Отладочный USB-порт платы и межплатный UART — разные каналы; обычные строки отладки монитор игнорирует.

## Статистика испытаний

```powershell
python -m tools.analyze_run examples/synthetic_run.csv --provenance synthetic --expected-parts 8 --output output/demo_run_report.json
```

В примере специально есть промахи, падение, неверный контейнер, тайм-аут и ручное вмешательство. Это искусственные записи для проверки формул, не результат испытания робота. Главная доля — правильное размещение с первой попытки без помощи. Повторы не удаляют первичный отказ. Если запланировано 100 испытаний, передавайте `--expected-parts 100`: незаписанные испытания останутся в знаменателе как неуспешные. Лучше заполнить каждую запланированную строку с реальным исходом, включая `aborted`.

`part_id` обозначает отдельное испытание детали внутри `run_id`. При следующем независимом предъявлении того же физического предмета нужен новый `part_id`, а повтор после промаха имеет тот же `part_id` и увеличенный `attempt_index`. Индексы начинаются с 1, без пропусков и повторов. После успешного испытания повтор с тем же идентификатором запрещён.

Столбцы CSV:

| Поле | Содержание |
|---|---|
| `run_id` | Название сеанса, например `session_01` |
| `part_id` | Идентификатор конкретного испытания детали |
| `attempt_index` | 1, затем 2 и т.д. при повторе |
| `expected_class` | Правильный класс: 1 — красный, 3 — синий |
| `placed_class` | Класс цвета контейнера: 1 — красный, 3 — синий; пусто, если размещения нет. Номер физического контейнера для синего — 2 |
| `outcome` | `success`, `wrong_bin`, `miss`, `pick_fail`, `drop`, `timeout`, `aborted` |
| `cycle_s` | Время попытки в секундах, включая ожидание и отказ |
| `intervention` | `true`, если понадобилась помощь человека; иначе `false` |
| `notes` | Что произошло |

`success` принимается только с правильным `placed_class` и `intervention=false`. Отчёт показывает статистику времени всех попыток, первых попыток и успешных попыток отдельно. P95 рассчитывается линейной интерполяцией позиции `(n−1)×0,95`; на малой выборке он не является устойчивой оценкой худшего времени.

## Состав и воспроизводимость

| Файл | Назначение |
|---|---|
| `protocol.py` | CRC16-CCITT-FALSE, строгие кадры UART и сцены, потоковый разбор |
| `calibration_picker.html` | Локальная разметка кадра, ручной ввод X/Y, экспорт train/test CSV |
| `calibrate.py` | Нормализованный DLT, проверка вырожденности, holdout, JSON/C++ |
| `serial_tool.py` | Явный USB-захват и пассивный монитор; pyserial необязателен |
| `analyze_run.py` | Проверка журнала, знаменатели с отказами, время и P95 |
| `generate_examples.py` | Повторяемые искусственные сцены, точки, журналы и эталонные пакеты |
| `new_session.py` | Пустая папка реальных измерений без перезаписи существующей |
| `check_picker.js` | Проверка синтаксиса страницы и пересчёта координат при масштабировании; Node.js |

```powershell
python -m tools.generate_examples
```

Последняя команда перезаписывает только заранее названные примеры в `examples`. Измерения пользователя храните отдельно в `measurements`, а не вместо `synthetic_*`. После изменения генератора повторно запустите тесты.

Дополнительно при установленном Node.js: `node tools/check_picker.js`. Эта проверка охватывает преобразование координат и синтаксис JavaScript; она не заменяет визуальную проверку страницы в браузере.
