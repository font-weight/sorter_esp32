AIMRED остаётся отдельной командой одного верхнего наведения; заново выполнять её сейчас не требуется.

## Автоматическая подсветка сканирования

При новом запросе управляющей ESP32 — CAMSCAN или обычном Q — камера сама включает белый LED **GPIO4**, ждёт **100 мс**, получает свежий кадр и сразу выключает LED перед обработкой. При ошибке получения кадра он также выключается. Повтор Q из кеша возвращает прежний ответ без новой съёмки и вспышки. Автоматическая подсветка также действует для USB SCAN/SCAN_MM, когда эти команды разрешены; CAPTURE/STATS используют ручные LED ON/LED OFF. Автоматический scan выключает LED после кадра, даже если перед ним был LED ON.

В CameraConfig.h установлены `SCAN_FLASH_ENABLED=true`, `SCAN_FLASH_SETTLE_MS=100`. Сборка текущей camera_node и программные проверки подсветки прошли. Для прежнего изменения подсветки требовалось перепрошить только ESP32-CAM; пользователь уже подтвердил LED. Это исторический контекст обновления камеры. В этапе 15 камера сохраняется; TRIALRED запрашивает один свежий кадр из **PARK 1500,1200,1500,2100** перед переносом и один из того же PARK после возврата и выдержки 800 мс. LED работает автоматически; прежняя HIGH над 20/80 остаётся только подходом к детали.

RGB-пороги сохранены. Если с новым светом появятся засветка, пропуски или путаница цветов, потребуется подстройка освещения/цветовых порогов по фактическому результату; геометрическую матрицу и координаты сейчас не менять.

## Этап 13: подтверждённая пользователем UART-диагностика, справка

Для связи подготовлены `CAMERA_PROFILE_CONFIRMED=true`, `CAMERA_UART_PINS_CONFIRMED=true`, `VISION_CONFIG_CONFIRMED=true`; в GeneratedCalibration.h остаётся `CALIBRATION_CONFIRMED=true`. Эти флаги разрешают профиль, а работу связи подтверждают пользовательское сообщение этапа 13 и итоговый STATUS этапа 14. Программные проверки и сборка camera_node/motion_node на ESP32 3.3.12 прошли. Сырые логи этапа 13 не предоставлены, агент аппаратуру не запускал. В этапе 15 обычные Q приходили из TRIALRED; этап 16 использовал AIMRED; в текущем этапе 17 кадры запрашивает SORT той же arm_calibration. UART, цвета, калибровка и автоматический LED прежние. Ниже оставлен справочный порядок завершённой диагностики.

1. Поддержать руку на опоре, выполнить DISARM в действующей ручной прошивке, выключить питание стенда и отключить **силовые 5 В сервоприводов**. Они остаются отключёнными весь этап. Руку закрепить так, чтобы она не закрывала камере поле; движение приводами не требуется.
2. При выключенном питании соединить напрямую 3,3-В UART:

   | ESP32-CAM | Управляющая ESP32-WROOM-32U |
   |---|---|
   | GPIO13, TX | GPIO16, RX |
   | GPIO14, RX | GPIO17, TX |
   | GND | GND |

   Последовательные резисторы и преобразователь уровней не нужны. GPIO13/14 заняты UART, microSD не использовать. Каждая плата получает питание от своего обычного USB/программатора; плюсовые 5 В двух источников не объединять. Общая земля обязательна, на UART подавать только 3,3-В уровни.
3. Загрузить `firmware/camera_node/camera_node.ino` в ESP32-CAM. Программатор использует штатные GPIO1/3 камеры; они остаются отдельной USB-консолью, их не заменять GPIO13/14. После загрузки снять перемычку IO0–GND для обычного запуска и перезапустить камеру. На управляющую плату загрузить подготовленный `firmware/motion_node/motion_node.ino` с командой CAMSCAN. Её конфигурация остаётся VIRTUAL_MODE=true, MOTOR_OUTPUTS_ENABLED=false, PINOUT_CONFIRMED=false; только UART_PROFILE_CONFIRMED=true. Геометрию, маршруты и парковочную опору не включать.
4. Монитор **камеры — 460800 бод**, окончание строки «Новая строка». Отправить **STATUS**. Ожидаемые поля: `CAMERA=1 UART=1 VISION_CONFIRMED=1 CALIBRATION=1 ID=1573755510`. CAMERA/UART=1 означают готовность своих модулей, а не уже проверенные провода.
5. Монитор **управляющей ESP32 — 115200 бод**. STATUS должен показывать `mode=VIRTUAL_NO_PWM`, `state=DISARMED`, `outputs=0`, `uart=1`, `camscan_pending=0`. Отправить **CAMSCAN именно сюда**, не в монитор камеры. Сначала выводится CAMSCAN_WAIT, затем CAMSCENE count=... calibrationId=1573755510 boot=... и OBJECT с class/color/x_mm/y_mm/pixels/in_pick_area. Команда делает один настоящий запрос Q и ждёт ответ D/E не более 6 секунд; ARM, PARKCONFIRM и синтетическая SCENE для этого этапа не нужны.
6. Сначала убрать детали и отправить CAMSCAN: ожидается сцена с count=0. Затем поставить отдельно красную и синюю детали внутри X=20…130, Y=25…80 мм, ближе к центральной области, например около 50/45 и 100/65. Точная раскладка здесь не требуется. Детали не должны касаться; вся их область должна оставаться внутри прежнего калиброванного участка камеры. При необходимости увеличить промежуток, сохранив обе внутри участка. Повторить CAMSCAN: ожидаются два объекта, красный класс 1 и синий класс 3, координаты в мм и площадь в пикселях.

**Результат этапа:** скопировать из монитора управляющей платы ответ CAMSCENE, строки OBJECT и следующий STATUS. При ошибке сохранить CAMSCAN_TIMEOUT или CAMSCAN_ERROR с кодом. Никаких новых POSE или ручных XYZ не требуется; пользователь затем подтвердил работу UART и LED без предоставления сырых логов. Рука остаётся без силового питания.

При включённом UART команды **SCAN и SCAN_MM на USB камеры заблокированы**: для текущей проверки использовать CAMSCAN на управляющей плате. CAPTURE/STATS также не запускать вместо рабочего запроса. Межплатный UART в обеих прошивках **115200 8N1**; 460800 относится только к USB-консоли камеры.

## USB-команды и справка первой настройки

Текущие разрешения уже включены для подготовленного профиля этапа 13; возвращать их в false или менять пороги и калибровку для этого этапа не нужно. Последовательность первоначальной настройки ниже сохранена как справка. USB-монитор камеры: **460800 бод**, LF/CRLF.
| Команда | Результат |
|---|---|
| `STATUS` | Чип, память, готовность, идентификаторы, настройки сенсора |
| `STATS` | Один свежий кадр: средний RGB, засветка/темнота, отпечаток |
| `CAPTURE` | Бинарный кадр для утилиты ПК |
| `SCAN`, `SCAN_MM` | Пиксельные области или миллиметры; только при UART выключен. В этапе 13 использовать CAMSCAN на другой плате |
| `HELP` | Список команд |

`CAPTURE`: `RGB565BE 320 240 153600\n`, 153600 байт, `\nEND\n`. Старший байт каждого RGB565-пикселя идёт первым. Битовые поля расширяются до RGB888 повторением старших битов. Для геометрической калибровки использовать именно эту прошивку и 320×240, не диагностическую 160×120.

В этой версии настройки OV2640 фиксированы: автоматические выдержка/усиление отключены, баланс белого выбран явно. Значения `SENSOR_EXPOSURE`, `SENSOR_GAIN`, `SENSOR_WB_MODE`, `SENSOR_HMIRROR`, `SENSOR_VFLIP` — начальные примеры. Подобрать выдержку под постоянную внешнюю подсветку; затем не менять её во время сбора изображений и испытаний. Перемещение камеры, изменение масштаба, ориентации, разрешения или плоскости деталей требует повторной геометрической калибровки; изменение освещения/экспозиции требует повторной проверки цветовых порогов.

## Последовательность калибровки

1. Закрепить камеру и свет, получить читаемый кадр через `CAPTURE`, проверить красный и синий эталоны. Классы: `1` — красный, `3` — синий; зелёный класс `2` отключён. SD и Wi-Fi не используются. Встроенный LED GPIO4 включается автоматически для нового сканирования; для CAPTURE подсветка управляется LED ON/LED OFF.
2. Снять реальные детали и фон. В `COLOR_RANGES` оставить ровно два включительных RGB-диапазона. Синий дополнительно требует `B > G + 15` и `B > R + 15`; красный сохраняет прежние условия RGB. Совпадение с обоими диапазонами или отсутствие доминирования синего даёт неопределённый цвет `0`. Настроить `DETECTOR_CONFIG`: ROI `[left,right)×[top,bottom)`, допустимую площадь в пикселях. `minChroma` — разность максимального и минимального каналов RGB. `SENSOR_WB_MODE=1`.
3. Проверить `SCAN`: несколько красных/синих деталей должны давать отдельные области; зелёный образец и белый/серый фон — ни одной. Соприкасающиеся одинаковые детали считаются одной областью; их физически разделять. Это выделение цветных областей, **не распознавание формы и не оценка ориентации**.
4. С помощью утилиты ПК получить `GeneratedCalibration.h`. Он содержит `sorter_calibration::{CALIBRATION_ID,CALIBRATION_CONFIRMED,IMAGE_WIDTH,IMAGE_HEIGHT,HOMOGRAPHY,SUPPORT_COUNT,SUPPORT}`. `SUPPORT` — выпуклый многоугольник 3–16 вершин без лишних точек на прямой. Матрица переводит полный кадр в миллиметры рабочей плоскости на высоте деталей. Проверить независимые контрольные точки, лишь затем подтвердить `CALIBRATION_CONFIRMED`.
5. После испытаний порогов, ROI, размера и фиксированных настроек включить `VISION_CONFIG_CONFIRMED`. Начальная единичная матрица и пороги примера не разрешают результат D.
6. Согласовать одинаковый `CALIBRATION_ID` с контроллером. Для изменения калибровки нужен новый ненулевой ID. Подтвердить отдельные провода UART и поставить `CAMERA_UART_PINS_CONFIRMED=true`.

## UART и кадры

Профиль текущей схемы KiCad: UART1, **115200 8N1**, RX=GPIO14, TX=GPIO13, 3,3-В логика и общая земля. TX камеры соединяется с RX контроллера, RX — с TX. Профиль допускает только эту пару; SD запрещена. Профиль нынешней ESP32-CAM уже использовался в проверках камеры. Внешняя связь с управляющей платой проверяется этапом 13; для иной распиновки нужен отдельный профиль. USB-диагностика остаётся на штатном UART0; управляющие пакеты идут по отдельному UART1.

Протокол описан в `sorter/INTERFACES.md`. На Q с ненулевым ID калибровки камера возвращает D или E. CRC проверяется общим `Protocol.h`. Повреждённые/неполные пакеты не запускают съёмку. Результат содержит максимум 8 объектов. При превышении лимита возвращается `TOO_MANY_OBJECTS`, а не урезанная сцена. Неизвестные цвета, слишком маленькие/большие области, области на краю ROI или выходящие за измеренный участок калибровки не передаются как цели.

Повтор последнего `(SESSION,SEQ,calibration_id)` возвращает **те же байты ответа**, включая ошибку, без нового снимка. Другой ID при том же SESSION/SEQ даёт `CONFLICT`; меньший SEQ в текущей сессии — `STALE`. Смена SESSION сбрасывает кэш. Переполнение SEQ требует новой сессии. Состояние старых сессий не хранится; на проводе должен быть один управляющий контроллер. После перезапуска камеры меняется `camera_boot`; контроллер обязан остановиться при его изменении.

Запрос снимает один объектовый кадр: старый буфер отбрасывается и проверяется время начала нового кадра. При автоматической работе кадр запрашивается из PARK. В этапе 13 рука неподвижна на опоре без силового питания и не закрывает поле; подтверждение парковки не требуется. Камера сама положение руки не измеряет. Бинарный захват/SCAN/STATS по USB запрещены при включённом UART, чтобы не задерживать рабочий запрос.

Алгоритм: пороги RGB → отдельные 8-связные компоненты → фильтр площади/границ → центр → гомография → десятые миллиметра. Память маски и очереди — **384000 байт PSRAM**, выделяется один раз. Дополнительно нужен кадровый буфер **153600 байт** и память драйвера. Обработка кадра не выделяет память и не кладёт большие массивы на стек. Реальная скорость на classic ESP32 требует измерения. При отказе датчика `fb_get` может ждать тайм-аут драйвера; контроллер должен обрабатывать собственный тайм-аут безопасно.

Основные E-коды: `CAMERA_NOT_READY`, `VISION_NOT_CALIBRATED`, `CALIBRATION_INVALID`, `CALIBRATION_MISMATCH`, `TOO_MANY_OBJECTS`, `CAPTURE_FAILED`, `NO_WORKSPACE`, `BAD_VISION_CONFIG`, `CONFLICT`, `STALE`. D с count=0 означает **нет допустимых распознанных целей**, а не доказательство пустоты стола или отсутствия препятствий.

Официальные API: [Espressif camera](https://github.com/espressif/esp32-camera/blob/master/driver/include/esp_camera.h), [sensor settings](https://github.com/espressif/esp32-camera/blob/master/driver/include/sensor.h), [время начала кадра](https://github.com/espressif/esp32-camera/blob/master/driver/cam_hal.c), [RGB565 byte order](https://github.com/espressif/esp32-camera/blob/master/conversions/to_bmp.c).
